# Reset the password of a User who forgot it

Status: ready-for-agent
Type: feature

> *This was generated by AI during triage.*

## Problem Statement

A User forgets the password and cannot start a Session. rastro has no route that changes a password, so only a manual change in the database restores the access.

## Solution

The User asks for a reset with the email address. rastro answers the same way whether that address has a User or not, and a worker sends an email with a link to the address of a User. The link holds a single-use Reset token that lives for 1 hour. The User opens the link and presents the Reset token with a new password. rastro then stores the new hash and ends every Session of the User, and the User starts a new Session with the new Credentials.

## User Stories

1. As a User who forgot the password, I want to ask for a reset with my email address, so that I can recover the access without an operator.
2. As a User, I want the reset email to hold a link, so that I can reach the new password step in one click.
3. As a User, I want the link to work for 1 hour, so that a delayed email still works.
4. As a User, I want to present the Reset token with a new password, so that the new password replaces the old one.
5. As a User, I want the old password to stop working after the reset, so that a person who knows it cannot start a Session.
6. As a User, I want the new password to follow the rule of the registration, so that a reset cannot store a weaker password.
7. As a User, I want the reset to end every Session of my User, so that a stolen Session token stops working.
8. As a User, I want to start a Session myself after the reset, so that the new Credentials are proved once.
9. As a User who asks twice, I want only the link of the last email to work, so that at most one valid link exists.
10. As a User, I want a used link to change nothing, so that an old email in my inbox cannot change the password again.
11. As a User, I want an expired link to change nothing, so that a forgotten email stops being useful.
12. As a User, I want rastro to ignore a second request within 60 seconds, so that a person who knows my address cannot flood my inbox at that rate.
13. As a person who probes rastro, I get the same response for a known address and an unknown address, so that the reset route does not tell who has a User.
14. As a person who probes rastro, I get the same response time for both kinds of address, so that a time measurement does not tell who has a User.
15. As a person with an unknown address, I receive no email, so that rastro does not write to people with no User.
16. As a client, I want a malformed email address to answer `422`, so that the client shows the error on the field, as in the other routes.
17. As a client, I want a used, expired, or unknown Reset token to answer one `400 auth.invalid_reset_token`, so that the client shows one message and the response reveals nothing about the token.
18. As a client, I want a successful confirmation to answer `204`, so that the client leads the User to the Session start.
19. As a User, I want rastro to retry the send while the SMTP server is down for a short time, so that a brief failure does not cost me the email.
20. As a User, I want rastro to send no second link when the SMTP server took the message and gave no answer, so that I do not receive a duplicate email.
21. As a User in that no-answer case, I want the link of the email to work if the email did go out, so that I do not receive a dead link.
22. As an operator, I want a send that exhausts its attempts or that the SMTP server refuses to end as a `failed` job, so that the job table and the error log show it.
23. As an operator, I want each reset job and its email address removed after 7 days, so that the job table does not keep every typed address forever.
24. As an operator, I want expired Reset tokens removed every hour, so that the table holds only tokens that can still work.
25. As an operator, I want to set the SMTP server, the sender address, the link URL, and the time limits through settings, so that each deployment uses its own values without a code change.
26. As a developer, I want Mailpit in the local stack, so that I can read the email that rastro sends without a real provider.
27. As a person who reads the database, I want to find only the digest of a Reset token, so that a leaked database changes no password.

## Implementation Decisions

### Routes

- `POST /api/v1/auth/password-reset/request` takes an email address. It answers `204` for every valid address and `422` for a malformed one.
- `POST /api/v1/auth/password-reset/confirm` takes a Reset token and a new password. It answers `204` on success, `400 auth.invalid_reset_token` for a used, expired, or unknown token, and `422` for a password that `RawPassword` rejects.
- Both routes run the CSRF check that `create_api_app` declares for every route.
- The confirmation starts no Session and does not touch the Session cookie.

### Request

- The request use case does not look up the User. It defers one job with the email address, so both kinds of address take the same path.
- This use case is the first that defers a job, so it adds the defer helper of ADR 0004. The job commits in the transaction of the request.
- The task takes the email address in its arguments, which is an exception to the rule of ADR 0004 and `CODING_STANDARDS.md` that a task takes ids. The maintainer accepted the consequence: the address sits in the job row and in the Procrastinate logs, including the logs that reach ClickHouse, and rastro adds no log filter. A one-line comment on the task states this exception.

### Task

The task opens one transaction, calls one use case, and commits after the send. The use case runs these steps:

1. It looks up the User by email. With no User, it ends and sends nothing.
2. It reads the current Reset token of the User. If that token is younger than the cooldown, it ends and sends nothing.
3. It generates a Reset token, and replaces the row of the User with the digest of the new token.
4. It sends the email through the port.

### Send outcomes

| Outcome of the send | Transaction | Job |
| --- | --- | --- |
| Accepted | Commit | Succeeds |
| Connection failure or SMTP 4xx | Rollback | Retries |
| SMTP 5xx | Rollback | Fails at once |
| Disconnection or timeout after the connection opens | Commit | Succeeds, with a warning log |

- A disconnection or a timeout after the connection opens may mean that the email went out. The commit keeps its link valid, and the job sends nothing more. If the email did not go out, the User asks again after the cooldown. This rule also skips the retry of a send that failed before the message body left, and the maintainer accepted that cost.
- A worker that dies after the send and before the commit runs the job again through `job_retry_stalled_task`. The User receives a second email, and only the second link works, because the first token never committed.
- The retry strategy of the task is a `RetryStrategy` with `exponential_wait=2`, `max_attempts=10`, and `retry_exceptions` limited to the temporary failure. The waits run from 2s to 1,024s and total about 34 minutes, and the job then ends as `failed`.

### Reset token

- `ResetToken` is a value object that wraps a `SecretStr`, with a `generate` method and a SHA-256 `digest`, in the shape of `SessionToken`. It has no format rule.
- A new table holds the digest, the User, the creation time, and the expiry. A unique constraint on the User keeps one Reset token per User, and the row goes away with its User.
- rastro stores the token in a table in place of a signed token. A signed token would need a new secret key, and the rehash in `session_start` would invalidate an open link.
- The worker generates the token, so the raw token never enters the job arguments.

### Confirmation

- The confirmation consumes the token atomically, so one of two concurrent requests succeeds and the other answers `400 auth.invalid_reset_token`.
- A valid confirmation removes the token, stores the new hash, and removes every Session of the User in one transaction.
- The use case hashes the new password only after the token proves valid.
- `SessionRepository` gains a method that removes every Session of one User.

### Email

- A new port sends one email. An SMTP adapter implements it for production, and a fake implements it for the tests.
- `create_worker_app` receives the adapter of the port, and the task reads it from the job context, as it reads the sessionmaker. A task test passes the fake the same way.
- The port reports the three failure kinds of the table above with distinct errors, so the use case and the retry strategy read no SMTP detail. The SMTP library is not chosen. Read the source of the chosen library before you map its exceptions to these errors.
- The email is plain text in en-US, with the link and its lifetime.
- The link is the configured URL with the token in the fragment, for example `#token=...`. A browser never sends the fragment, so the token stays out of access logs and the `Referer` header.

### Settings

New settings hold the SMTP host, port, user, password, and transport security, the sender address, the link URL, the Reset token lifetime (default 1 hour), the cooldown (default 60s), and the Reset token size in bytes.

### Cleanup

- The hourly task that removes expired Sessions has a counterpart that removes expired Reset tokens.
- A daily periodic task runs Procrastinate's `remove_old_jobs` on the queue of this task, with `max_hours=168` and `remove_failed=True`.

### Local stack

The compose stack gains Mailpit, and the local environment points the SMTP settings at it.

## Testing Decisions

A test covers external behaviour: the HTTP response, the rows that a second session reads, the email that the fake received, and the state of the job. Each kind of test follows the section on tests in `CODING_STANDARDS.md`, so no test uses `mock.patch`.

- **Domain tests** cover `ResetToken` and the aggregate of the Reset token, including its expiry. Prior art: the tests of `SessionToken` and `Session`.
- **Use case tests** cover the rules with fakes: no User, the cooldown, the replacement of a token, each send outcome, the used, expired, and unknown token, and the Sessions that a confirmation removes. Prior art: the tests of `session_start` and `session_end`.
- **Repository tests** run the behaviour suite of the Reset token port against the fake and the Sql adapter, and extend the suite of `SessionRepository`. A Postgres-only test covers the atomic consumption and the unique constraint. Prior art: the Session repository suites.
- **View tests** compare the literal JSON of each problem and assert that the request route gives the same response for both kinds of address. Prior art: the view test of `session_start`.
- **Task tests** run the worker on `InMemoryConnector` with the fake email port and assert the retry, the failure, and the commit of each send outcome. Prior art: the test of `session_remove_expired_task`.
- **An adapter test** runs the SMTP adapter against a local test SMTP server and maps each server response to a port error.
- **One flow test** walks the first acceptance criterion across the request route, the worker, and the confirmation route.

## Acceptance criteria

- [ ] Given a User, when the client asks for a reset, the worker runs, and the client presents the token of the email with a new password, then the Credentials with the new password start a Session, and the old password does not.
- [ ] Given a User with active Sessions, when a confirmation succeeds, then every Session of the User has ended.
- [ ] Given a Reset token that was used once, when the client presents it again, then the response is `400 auth.invalid_reset_token`, and the password stays the same.
- [ ] Given two requests of one User more than 60s apart, when the client presents the first token, then the response is `400 auth.invalid_reset_token`, and the second token works.
- [ ] Given two requests of one User within 60s, when the worker runs both jobs, then one email goes out.
- [ ] Given an email address with no User, when the client asks for a reset and the worker runs, then the response equals the response for a known address, a job exists, and no email goes out.
- [ ] Given an SMTP 4xx, when the job runs, then no token commits, and the job retries.
- [ ] Given an SMTP 5xx, when the job runs, then no token commits, and the job ends as `failed` with no retry.
- [ ] Given a timeout after the connection opens, when the job runs, then the token commits, and the job does not retry.
- [ ] Given an email that went out, when a test reads the Reset token table and the job arguments, then neither holds the token of the link.
- [ ] Given an expired Reset token, when the client presents it, then the response is `400 auth.invalid_reset_token`, and the hourly task removes the row.
- [ ] Given a finished job older than 7 days, when the daily task runs, then the job row is gone.

## Out of Scope

- A password change for a User who knows the old password.
- A rate limit per IP on the request route.
- The enumeration through `POST /api/v1/auth/register`, which `.scratch/ideas/0009-stop-register-from-telling-who-has-a-user.md` covers.
- A log filter for the email address in the Procrastinate logs.
- The frontend and the screens. The code flow in `docs/design/index.excalidraw` is an experiment, and this spec is the source of the flow.
- A record of each request and its outcome. The job row and the log hold the outcome.
- An HTML email template.

## Further Notes

- To deploy this with a provider's SMTP relay, turn off its click tracking for this email. Click tracking rewrites the link, so the provider receives the token.
- `CODING_STANDARDS.md` keeps an email out of a log through `hide_input_in_errors`. The email address in the job logs is an accepted exception to that goal, so a change to this decision needs the maintainer.
